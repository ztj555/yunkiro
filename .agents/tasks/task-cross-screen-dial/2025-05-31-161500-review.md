# Cross-screen one-click dialing system via WebSocket relay

A four-component system enabling a desktop PC to trigger phone calls, hangups, and SMS on a paired Android phone over a centralized WebSocket relay. A browser extension detects Chinese mobile numbers on web pages and sends dial commands through the same channel. PIN-based grouping isolates tenants; the relay routes messages by role (PC sends commands, phone sends results). The relay is a stateful Go server; the PC client is a Tauri v2 app with React frontend and Rust backend; the Android app runs a foreground service; the extension is MV3 Chrome.

**Watch for:** The extension connects to a **different local WebSocket endpoint** (`ws://localhost:8765`) with a protocol that doesn't match the relay at all (confirmed). PIN credentials are stored in Android SharedPreferences as plaintext (confirmed). The relay accepts connections from any origin with no authentication beyond a 4-digit PIN (confirmed). The Android app sends `ack` messages that the relay simply consumes and never forwards, but the PC client never sends or expects acks, creating a one-sided reliability assumption (confirmed).

## High-level view

The relay server fans connections into PIN-keyed groups, broadcasts phone presence events to PCs, and uses a heartbeat reaper to prune stale connections. Routing enforces a role-direction invariant (PCs command phones, phones return results). The integration test suite covers the main flows end-to-end using real WebSocket connections.

The PC client exists in two modes: a Tauri/Rust backend managing the WebSocket lifecycle (reconnect loop, ping task, event emission), and a browser-fallback direct-WebSocket path in the React hook. Both speak the same relay protocol.

The Android client wraps OkHttp's WebSocket in a foreground service with exponential backoff reconnection and a ConnectivityManager callback to eagerly reconnect on network restoration. A `MessageHandler` layer adds message-ID deduplication and sends ACKs—a reliability layer that no other component participates in, creating a protocol asymmetry.

The browser extension operates on a completely different protocol layer: it connects to `ws://localhost:8765` (presumably a future local bridge in the PC app) using a simplified schema without `message_id`, `device_id`, `pin`, or auth handshake. It cannot communicate with the relay server as-is.

<summary>Issues (8)</summary>

1. **Extension protocol mismatch** — The extension connects to `ws://localhost:8765` with a minimal `{type: "dial", phone_number}` message. This is incompatible with the relay's auth-first protocol. Either implement a local bridge (PC client exposing 8765) or make the extension speak the relay protocol directly.
2. **PIN stored as plaintext on Android** — SharedPreferences stores the PIN unencrypted. Use EncryptedSharedPreferences (Jetpack Security) to protect credentials at rest.
3. **4-digit PIN as sole authentication** — Only 10,000 possible PINs, no rate limiting on auth attempts. An attacker can enumerate PINs quickly by connecting repeatedly. Add a connection-level rate-limit or switch to a longer secret.
4. **One-sided ACK assumption** — Android sends ACKs and deduplicates by `message_id`, but the relay discards ACKs silently and neither the PC nor relay guarantee at-most-once delivery. Document the contract or remove dead ACK code.
5. **Android heartbeat may not reach relay** — OkHttp sends WebSocket-level ping frames, but gorilla/websocket handles those transparently without triggering `ReadMessage`. The relay's 45s inactivity reaper may kill idle Android connections. The Android client should send application-level `{"type":"ping"}` messages like the PC does.
6. **WakeLock without renewal** — `KeepAliveService` acquires a 10-minute WakeLock once. The service is START_STICKY and runs indefinitely. After expiry the CPU may sleep, stalling message processing. Renew periodically or remove entirely (OkHttp's I/O thread may suffice with foreground service guarantee).
7. **No error response for unreachable phone** — When a PC targets a disconnected phone, `RouteToPhone` returns false silently. The PC gets no `dial_result` and has no timeout. Add a relay-generated error response or a client-side timeout.
8. **No TLS** — All sample URLs use `ws://`. Credentials (PIN) travel in cleartext. If deployed beyond a LAN, wss:// is mandatory.

## Extension's standalone protocol and the relay gap

The extension's `background/index.ts` hardcodes `ws://localhost:8765` and speaks a simplified protocol: it sends `{type: "dial", phone_number: "..."}` and expects `{type: "dial_result", success, error}` or `{type: "status", connected, phones}`. There is no auth handshake, no PIN, no `message_id`, no `device_id`, no `role` field. The relay server will reject this connection immediately because it expects an `auth` message within 5 seconds of connect.

The implicit contract is that the PC client exposes a *local* WebSocket server on port 8765 that bridges the extension to the relay. But this bridge does not exist anywhere in the codebase. The extension is effectively inert until that bridge is built or the extension is rewritten to speak the relay protocol directly.

## PIN security and relay trust model

The relay authenticates solely via a 4-digit numeric PIN. `handler.go` checks the format but imposes no rate limit. There is no per-IP or per-connection backoff, meaning an attacker with network access can try all 10,000 combinations in under a minute by opening connections in parallel.

On Android, the PIN is persisted in `SharedPreferences` (`yunkiro_prefs`, key `pin`) without encryption. The BootReceiver reads it and passes it to the service. On a rooted device or via adb backup, the PIN is trivially extractable.

The relay's `CheckOrigin` always returns `true`, and no TLS support exists. Together these mean: anyone on the same network can sniff the PIN off the wire, then connect and issue dial/SMS commands to the phone. For LAN-only use this may be acceptable, but it must be a documented threat model, not an accidental gap.

## Android's ACK/dedup layer vs. rest of system

`MessageHandler.kt` tracks processed `message_id` values in a bounded LRU set (100 entries). On receiving a command (`dial`, `hangup`, `sms`), it sends an `ack` message back to the relay and only processes the command if the ID hasn't been seen before.

The relay hub's `Route` function has a case for `TypeAck` that logs and discards:
```go
case protocol.TypeAck:
    h.log.Debug("ACK received from device=%s", conn.DeviceID)
```

Nobody reads these ACKs. The relay does not retry based on ACK absence, and the PC client neither sends ACKs nor deduplicates incoming messages. The Android side is protected against double-processing, but the PC side is not. If the relay or network path ever duplicates a `dial_result`, the PC frontend will process it twice.

## Heartbeat timing: Android connections at risk of reaping

The relay reaps connections after 45 seconds of inactivity (`HeartbeatTimeout`), checking every 15 seconds. The PC clients send application-level `{"type":"ping"}` every 30 seconds, which hits `ReadMessage` and updates `lastActivity`.

The Android `RelayConnection` configures `OkHttp.pingInterval(30_000ms)`, which sends WebSocket-level ping *frames*. gorilla/websocket on the relay side handles pong frames transparently at the library level without surfacing them to `ReadMessage`. The `TouchActivity()` call in `readPump` only fires on data frames.

If an Android phone is idle (no dial commands, no status changes) for 45+ seconds, the relay will close it as stale—even though OkHttp-level pings are flowing. The relay never sends server-initiated pings, so the Android's `onPing` callback (which sends an app-level pong) never fires. The fix is for the Android client to send periodic application-level `{"type":"ping"}` messages, matching the PC's behavior.

## WakeLock lifetime in KeepAliveService

```kotlin
acquire(10 * 60 * 1000L) // 10 minutes max
```

After 10 minutes the lock auto-releases. The service is `START_STICKY` and intended to run indefinitely. Once the WakeLock expires, the CPU can suspend, stalling the WebSocket read loop. OkHttp's WebSocket-level pings may keep the TCP connection alive, but application-level message processing (incoming dial commands) stops until the next wakeup event.

## No error for commands targeting disconnected phones

The hub enforces directional routing: `dial`/`hangup`/`sms` only from PCs, forwarded to a specific phone by `device_id`; results only from phones, broadcast to all PCs. When a PC sends a `dial` command targeting a phone that has disconnected between the `phone_online` event and the command, `RouteToPhone` returns false and the relay logs a warning—but no error response goes back to the PC. The PC waits indefinitely for a `dial_result` that never arrives. The frontend `useRelay.ts` has no timeout mechanism for pending commands.

## Test coverage

**Not tested:** reconnection behavior under network failure in any client; the extension-to-PC bridge (doesn't exist); multi-message ordering under concurrent commands; the heartbeat reaper actually closing stale connections in integration; the Android WakeLock/foreground-service lifecycle; the PC frontend receiving no response when targeting a disconnected phone.
